## grzeb 检索语义扩展（core 层已写完，**尚未跑通验证**）

### 项目坐标
- Kotlin Multiplatform，targets = `jvm()` / `wasmJs { browser() }` / `android()`（**无 iOS**）。
  `core` 必须在 `commonMain` 三端通用 ⇒ 任何 JVM-only 库都用不了。
- 检索 UI 在 `shared/.../ui/search/`；引擎在 `core/.../core/search/SearchEngine.kt`，
  移植自 react 版 `lib/search/{types,engine}.ts`。SAF 是 Android 侧的 IO 瓶颈。

### 已实测确认的两个 bug（不是推测）
1. **跨行匹配做不到**：`buildRegex` 只加 `MULTILINE`，没加 DOTALL ⇒ `.` 不跨行。
   JVM 实测 `张三.*卡号` 对 `张三\n卡号` = `false`；必须 `(?s)` 或 `[\s\S]*?`。
2. **中文 + 全词匹配 = 恒 0**：`isWholeWord` 拿 `\b` 包裹，而 JVM 的 `\b` 基于 ASCII `\w`。
   `\b张三\b` 在「这是张三的书」「abc张三」「张三 说」**全部 false** ⇒ 恒假 pattern，
   界面只显示"没有找到匹配的结果"。中文小说场景必踩。

### 本轮改动（core 层，纯增量、全部带默认值）
- 新增 `core/.../search/QueryParser.kt`：分词（半角/全角空格 U+3000 / NBSP U+00A0 / Tab / 换行）、
  `"短语"`（含 `“”`）、`-排除词`（引号内不当排除）、三种模式（字面量 / 通配符 / 正则）。
  通配符 `*` → `[\s\S]*?`（跨行非贪婪）、`?` → `[^\n]`；**不能用全局 `(?s)`**，否则 `?` 也跨行。
  正则模式不切词（切了会破坏 `a{1, 3}` / `\d+ \w+`）。
- `SearchOptions` 增 `isWildcard` / `isMultiKeyword`（默认 false ⇒ 行为与 react 版一致）。
- `searchInContent` 改为多 pattern 文件级 AND + 排除词 + 每词首个 + 按 start 排序；
  新增 `MAX_MATCHES_PER_FILE = 500`（截断只影响展示，不影响"是否命中"判定 —— 用 `hits` 判）。
- 保留 `SearchEngine.buildRegex(options)` 不动：并发写入方的 UI 用它做校验。
- 测试已写：`core/src/jvmTest/.../QueryParserTest.kt`、`SearchEngineTest.kt`（假 GrzebFileSystem）。
  **`:core:jvmTest` 尚未跑过。**

### 未决：要不要改用现成检索引擎
- Lucene / `lucene-kmp` / kromus / FTS5 都是**倒排索引 = 词元匹配**，
  答不了"跨行 `*` / 任意正则 / 全词 / 精确大小写"这类 **span 语义**；
  引进来之后仍要在原始正文上 verify 一遍 ⇒ 只会变成"引擎 + 原匹配器"两份都在，不是替换。
- ripgrep（同一套语义的参考实现）**故意不做索引**，直接扫 —— 当前架构的有力旁证。
- `lucene-kmp` 10.2.0-alpha14 **不含 wasmJs**；`kromus` 0.16.0 **pre-1.0**。
- 真正值得"用现成的"的是商品化部分：编码探测（juniversalchardet / ICU4J）、
  文件名模糊的打分算法、正则（已用平台自带 java.util.regex / JS RegExp）。
- 待定：若日后实测发现"二次检索 CPU"才是真瓶颈，再考虑 FTS5 只做**预筛**分支；
  前提是先确认 Android 系统 SQLite 与 wasm 侧 SQLite 是否带 FTS5 + trigram。

第一次跑 `:core:jvmTest` 挂在 `SearchEngine.kt:172 Unresolved reference 'plan'`：
`searchInContent(..., plan)` 已按多关键词重构，但 `search()` 仍在传不存在的 `plan`。
**等我去修时，读盘发现已被改成局部 `val plan = QueryParser.parse(options)`** ——
我按快照补的字段成了死代码 + 撞名，遂删除。（core 也在被并发改，见 `stale-build-error-attribution`。）

### 实测（SQLite 3.53/3.54；脚本 `/tmp/fts_probe.sql`、`/tmp/fts_bench2.py`）
- **FTS5 默认分词器 unicode61 对中文子串全盘 0**：它把**整段连续 CJK 当成 1 个 token**，
  `fts5vocab` 导出确认 `这是张三的银行卡号信息` → token 就是 `[这是张三的银行卡号信息]`。
  ⇒ `MATCH '卡号'` = 0，`MATCH '银行卡号'` 也 = 0。中文子串不是"不擅长"，是**原理上查不到**。
- **trigram 是唯一能子串的方案，但 3 字门槛正好卡死中文高频查询**：`MATCH '卡号'`(2字) = **0 命中**；
  `LIKE '%卡号%'` 用不上索引（EQP = `SCAN t VIRTUAL TABLE INDEX 0:L0`）且**比全表扫还慢**
  （43.1ms vs 36.7ms）。4 字以上才真快：`银行卡号` 43ms → 0.1ms（约 400×）。
- **索引 +139% 体积**（同一份 6.0M 字符语料：18.0MB → 43.0MB），而 `content` 表还得留着。
- **全表扫很便宜**：6.0M 字符 ≈ 40ms；且这是 C 级 LIKE（对扫描方偏乐观，Kotlin `Regex` 会更慢）。
- `minSdk 24` 对应 SQLite 3.9，而 **trigram 需要 3.34+** ⇒ 老机器上这个分词器不存在。
- 踩过的坑：第一版 benchmark 语料只有 15 个词、**每个文档都命中全部查询词**（零剪枝 =
  索引最坏情况），数字全错、必须重做。**测索引必须先造出真实选择性。**

### 结论
放开「跨行 `*` / 任意正则 / 全词」这三项**不改变结论**：卡住索引的从来不是它们，
而是**「子串」+「中文」**。若把要求再松到「只做**词**匹配、放弃子串」，现成引擎立刻赢，
但那样 `卡号` 永远搜不到 `银行卡号`。
⇒ 真卡点是**子串**；正则反而是索引唯一能配合的东西（抽字面量做预筛，即 ripgrep 的架构）。
⇒ 日后真要加索引，正确形态是**自建 n-gram 倒排表当预筛 + 扫描兜底**（能覆盖 2 字查询），
  而不是 FTS5。触发条件：实测证明"二次检索 CPU"才是瓶颈。

### 更靠前的缺口（比 FTS5 更该先解决）
**索引层目前完全没接线**：全仓库没有任何 Kotlin 代码引用 `GrzebIndex` / `SqlDriver` /
